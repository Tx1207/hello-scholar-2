# Takeoff

The user need not name this skill, but direction exploration must belong to the current task. Do not turn a bounded fix or an accepted implementation request into unsolicited goal redesign.

Rejudge the target before optimizing the current approach. Recover the existing goal, inherited constraints, and available evidence. Distinguish real contracts from assumptions, habit, and implementation inertia.

Offer a clear higher-leverage thesis, explain what it replaces, and compare it with conservative and staged alternatives. Name the concrete payoff, principal cost, largest uncertainty, a cheap proof point, and evidence that would falsify the thesis. Keep target design separate from migration mechanics.

Do not force compatibility without an external contract, collapse the ambition into a tiny first step, or descend into code detail that does not affect direction. The output should help the user choose a direction, not prescribe a fixed document or implementation sequence.

When the same request asks for both takeoff and landing, first open the space and then test the preferred direction for feasibility using the `landing` criteria. Do not require a later turn or another phase approval.
