## 1. 产品目标和范围

hello-scholar 提供模型无法自行得知的项目约定、持久设计和科研证据格式。用户给出目标或 Spec 后，Agent 自行理解代码、安排步骤、实现和验证。

新版默认流程为 `用户请求 + Spec（需要时） → 实施 → 验收证据`。Spec 记录目标，代码体现实现，测试和 Record 支撑结论，Architecture 描述已采用的系统，Handoff 保存跨会话继续工作所需的上下文。

本次交付取消独立的 `plan.md`、`tasks.md` 写入流程及其运行时依赖，不新增执行 Skill、强制 execution.md 或另一套审批状态。保留原有 Spec、Record、Architecture、Handoff 路径。实现使用现有 Node 标准库和解析能力，不增加运行依赖。

### 用户可观察的行为

| 用户请求 | Agent 的行为 | 正常停止点 |
| --- | --- | --- |
| 修复局部问题 | 读取相关代码，修复并做相关验证 | 问题修复或具体阻塞；不补建 Spec |
| 给一个设计方案 | 澄清影响结果的选择，交付可评审方案；需要持久 Spec 时写草稿 | 方案或 Spec 草稿交付 |
| 按已给出的 Spec 实现 | 直接实施、验证并记录验收结果 | 验收完成或确实需要新决定 |
| 设计并实现某项能力 | 常规选择依据项目事实处理；重大未决行为先澄清，再继续已授权实施 | 实施和验证完成 |
| 继续上次工作 | 从指定 Spec、代码、证据及可用 Handoff 恢复 | 当前授权目标完成或具体阻塞 |
| 对照 Spec 检查 | 不论实现进度，直接给出缺口和依据 | 审计结果交付 |
| 对照 Spec 检查并修复 | 审计后继续修复范围内缺口并验证 | 缺口关闭或需改变目标的决定 |
| 正式实验或保存实验结果 | 保留复现信息、一次真实运行的原始输出和终态 | 用户要求的运行或监测边界 |

Spec 的 `accepted` 表示目标已确定，不代表外部发布权限。明确指定 draft Spec 并要求照此实现，可视为接受该版本，但先解决文档中实际影响实现的未决项；不再单独询问“是否批准路径”“是否批准任务”“是否开始实施”。

## 2. 技能组合与职责

保留现有名字，避免为名称变更增加安装迁移。九个保留技能全部随默认安装提供；安装可用与何时调用分别处理，调用仍根据用户请求和技能职责判断。

| 分发方式 | Skill | 新职责与触发 |
| --- | --- | --- |
| 默认安装 | `manage-specs` | 创建、修订或替代持久 Spec，保存设计决定、约束与验收要求 |
| 默认安装 | `record-experiment` | 需要持久科研证据或成本显著的运行，维护运行身份和证据 |
| 默认安装 | `converge-to-spec` | 用户要求对照 Spec 审计实现时使用，不成为每次完成的必经步骤 |
| 默认安装 | `docs-maintenance` | 用户要求文档检查、索引、恢复，或实施导致现有架构说明需要更新 |
| 默认安装 | `handoff` | 保存下次会话真正需要的状态和剩余工作 |
| 默认安装 | `grilling` | 用户需要交互式质询时，逐个问题压力测试方案 |
| 默认安装 | `crash-audit` | 审查风险、证据或推进条件时，识别关键不确定点和遗漏 |
| 默认安装 | `takeoff` | 任务包含方向探索或假设挑战时，重判目标并扩大设计空间 |
| 默认安装 | `landing` | 设计需要资源、兼容性或停止条件判断时，检验现实可行性 |

按当前任务语义选择技能，不要求用户点名。自动触发不增加授权：普通小修复不扩张为战略讨论或质询，已确定的实施范围不重新打开，文件中的关键词不构成用户请求。

退休 `writing-plans`、`generating-tasks`、`using-helloscholar` 和 `brainstorming`。需求探索与方案讨论由模型直接完成，需要持久设计时使用 manage-specs。TDD、worktrees 和 writing-great-skills 移出可安装技能目录，仅将仍有价值的科研测试模式、平台边界和技能维护说明整理到 `docs/`。通用 TDD 和 Git 操作仍可由用户直接要求，框架不强制加载对应教程。

### 保留技能的具体变化

- `manage-specs`：内部包含“新建、修订、替代”三个分支。共同入口仅包含职责、所需输入和完成条件；按分支读取身份、修订与模板参考。归属明确时自行选路径；仅多个同等合理归属才提问。已存在的 Spec 不因模板更新而整体重排。
- `record-experiment`：入口先区分临时观察、正式运行、已有 Run 更新；普通测试不需要解释一遍为何未建 Record。正式运行只执行一次并同时捕获 stdout/stderr；字段、远程运行和派生产物说明按需读取。
- `converge-to-spec`：逐个核对验收要求，报告事实、严重程度、证据和修复方向。支持部分实现和 draft Spec 的对照，明确比较的修订及草案属性。审计本身保持只读；“检查并修复”时当前执行者继续修复并验证。
- `docs-maintenance`：保留四种操作，但允许在已授权目标内顺序组合。例如恢复时先 check，再 sync，再更新已核实的文档。只要求 check 时严格只读。Architecture 在已有授权内更新；并发变化时重读并合并受影响事实。
- handoff、grilling、crash-audit、takeoff、landing：保留独特的输出目的，删除固定数量的标题、强制最后提问和相互跳转。用户同轮要求 takeoff 与 landing 时可以顺序完成。grilling 的结束条件是与当前目标相关的关键决定已明确，不穷尽想象中的未来分支，不强制派遣子 Agent。

每个 description 使用一句明确的适用条件，不罗列同义触发词，不写“任何工作前必须调用”。正文只保留会改变结果的契约；示例和分支细则按需读取。长度统计用于发现负担，不把固定行数、token 数或标题数量变成新的合格门。

技能质量是本次改进的首要判断依据。先明确要验证约定复用能力，还是约定已知时的额外指导收益：前者用自然请求和可用产物，后者用同条件的无目标技能对照。只在真实问题支持时重写，并按对应标准验证。具体方法和九个技能的指标统一见 [技能质量评估方案](skill-quality-evaluation.md)，不以文件更短、技能更少或自评分更高作为成功结论。

中英文镜像在同一修改中保持含义一致，运行时只读取选中的入口与相关参考，不要求双语全文同时加载。平台调用开关分别适配；不能假定某平台字段在另一平台也会隐藏描述。

## 3. AGENTS 与安装模板

采用职责不同的两类来源：

- 根 `AGENTS.md` 与 `CLAUDE.md`：分别是安装到使用者项目的完整通用工程规则，两者保持相同正文且可独立使用。`AGENTS-zh.md` 是中文核对版。
- `CONTRIBUTING.md` 及 `docs/maintenance/repository-guide.zh_CN.md`：保存本仓库代码位置、开发命令、测试边界和技能维护要求，不分发到业务项目。根规则要求修改前阅读项目已有的 README 和贡献指南，为这些本地要求提供明确阅读入口。

两种工具的安装器统一读取根 `AGENTS.md`，放入各自的 AGENTS/CLAUDE marker；源码 `CLAUDE.md` 仍链接到相同正文。这样实际 npm 包无需携带符号链接，也不维护第三份安装模板。中文镜像用于维护核对，不新增安装语言选项或 AGENTS 自然语言解析。正文使用英文不决定用户回复和业务文档的语言，规则明确当前任务语言优先于项目默认；用户写在管理块之外的偏好继续有效。

通用正文恢复上下文阅读、假设、简洁、精准修改、验证、调试、依赖、注释和安全原则；以下是 Spec 驱动部分的摘要，不代替根文件的完整规则：

> 根据用户目标和相关项目事实完成工作；需要持久设计时使用 Spec。用户要求实施时，自主安排步骤、实现、运行相关验证，并更新本次变更影响的现有文档。已给出的授权持续有效；关键产品选择无法从事实确定，或下一步超出授权范围时再询问。只要求分析、设计或审计时交付对应结果。
>
> Spec 位于 `hello-scholar/specs/`，当前架构位于 `hello-scholar/architecture.md`，正式实验记录位于 `runs/<run-id>/record.md`，交接位于 `hello-scholar/handoffs/`。INDEX 由 `hello-scholar docs sync` 生成，`docs check` 只读。临时步骤使用可用的原生任务工具，不生成或审批 plan.md、tasks.md。
>
> 保留用户修改与真实外部契约。正式实验保留命令、输入、环境、原始输出和结论；大文件和实验产物不默认加入 Git。完成时说明结果和实际验证，相关检查通过后，只有新修改、失败或未决疑点才需要继续验证。
>
> 输出和写入文档优先使用当前任务明确指定的语言，否则遵循目标文件或项目语言。注释解释不明显的契约、原因和影响。

`CONTRIBUTING.md` 保存本仓库实际开发命令：`npm test`、`npm run test:js`、`npm run test:py`、`npm run docs:check`。这些命令不进入通用安装正文。允许在一次授权内运行相关本地检查、修复本次变更导致的失败并复测；实际测试环境边界以检查过的测试和 fixtures 为准。付费模型评估、远程训练不混入普通测试命令。

用户指定的 hello-scholar 回复模板保留在通用根规则并随安装分发；本仓库中文偏好和验证命令保留在贡献指南，业务项目沿用自身语言和验证命令。

## 4. Spec、执行状态和验收

### 路径与字段

继续使用 `hello-scholar/specs/<topic>/SPEC-NNN-<name>/spec.md`。Spec 保持 `schema: 1` 和现有身份字段，不新增 `approved_revision`、`plan_revision`、任务图或执行审批字段。

沿用现有七部分模板：价值与决定、当前事实、目标与非目标、目标设计、接口与不变量、实施边界、验收与验证。七部分是默认写作骨架，不按字面标题检查业务正确性。只有真实迁移需求才增加迁移和回滚细节。

### 验收记录

每个验收要求使用稳定的 `AC-01` 等标识，在验收章节就地记录结果。以下仅示意记录方式，不代表这些实现已经存在：

| 验收项 | 要求 | 当前结论 | 证据 |
| --- | --- | --- | --- |
| AC-01 | 没有 Plan/Tasks 的 Spec 可以检查和生成索引 | 待验证 | 无 |
| AC-02 | 已有关联实验不因退休 Plan 而丢失归属 | 部分满足 | 已有代码检查；兼容测试未运行 |

实际证据写明所覆盖的 Spec 修订、实现版本或工作树变化、命令和结果；正式运行链接对应 Record。不存在可信命令时使用代码证据并说明局限，不补造日志。表格是人类可读事实，不设计新的 Markdown 状态解析器或由它计算完成百分比。

临时微步骤与并行安排由 Agent 管理，平台任务工具不可用不阻塞工作。跨会话恢复先读 Spec 的剩余验收缺口，再核对实现；Handoff 只保存代码和验收章节尚不能恢复的上下文。

### 状态与修订

| 事件 | Spec 处理 |
| --- | --- |
| 目标尚未确定 | `draft` |
| 用户接受目标或明确要求按该版本实施 | `accepted`；有关键未决项时先解决 |
| 开始实施或部分完成 | 仍为 `accepted`；在验收章节写真实进展，不增新状态 |
| 当前修订的全部验收要求满足 | `completed` |
| 同一目标的已完成实现发生偏差 | 修复期间回到 `accepted`，目标不变则 revision 不增 |
| 范围、行为、接口、不变量或验收要求改变 | revision 加一；只有新目标尚未被用户确定时保持 draft |
| 只补充执行证据、格式或生命周期状态 | revision 不变，更新 `updated` |
| 用户明确放弃工作 | 沿用 `withdrawn`；不因切换会话或目标而自动撤销 |

完成不能从 Tasks 勾选、历史“通过”总结或索引状态推断。Spec 更改后重新核对受影响证据，保留仍有效的部分。旧修订引用仍是历史事实，但不能自动证明新修订已完成。

替代设计先在草案正文说明拟替代目标。新设计已经实现、验收且被采用后，才同时写入双方 `supersedes` / `superseded_by` 并把旧 Spec 标为 `superseded`。明确的替换实施请求可以包含采用授权；不另设必经采用审批。这样保留现有双向关系校验，也避免新 draft 使现有契约过早失效。

## 5. 文档 CLI 和历史数据

### 新行为

- `docs check` 继续只读，`docs sync` 只更新可证明由工具生成的索引。解析错误和不安全写入目标仍阻止 sync，已有原子更新与回滚行为保留。
- 新索引只展示 `Topic / Spec / Type / Status / Revision / Summary`，Topic 索引保留替代关系。移除 Plan/Tasks 状态、审批和完成百分比，状态仅表示文档声明。
- Spec 没有 Plan/Tasks 是正常情况，不产生对应 missing notice。历史 Plan/Tasks 不进入当前执行决策，也不要求继续更新。
- 新 Record 使用 `schema: 2`，沿用当前字段但删除 `plan_revision`。`spec` 与 `spec_revision` 同时为 null 或同时有效；后者须引用存在的 Spec 且不得指向未来修订。允许正式探索关联 draft Spec，也允许独立 Run 不关联 Spec。
- 新 Run 一次捕获实际命令输出，真实状态和时间沿用 Record 的事实约束；负结果与运行故障继续区分。此改进不顺带重设其他实验生命周期语义。

### 兼容范围

此前建议的新 schema 收敛为仅用于 Record。Spec 和 Architecture 的字段没有破坏性变化，继续 schema 1，避免全项目升级。

历史 `schema: 1` Record 保留原文和 `plan_revision`，读取时仍检查其类型、关联字段完整性、Run 身份与时间合法性。当前索引只使用 Spec 关联。找不到历史 Plan 或无法证明其修订时给历史溯源 notice，不用这个旧执行层阻止当前工作；缺失 Spec、非法字段和伪造未来 Spec 修订仍是错误。

原来的 plan.md、tasks.md 作为历史材料发现并报告，不作为当前核心文档解析或阻止 sync。可能承载独有需求的旧文档不能直接删：用户启动对应目标的迁移时，先核对旧 Plan/Tasks，将仍有效的行为约束并入 Spec、完成事实附入验收证据，纯步骤保留为历史参考。迁移之前的 Spec-only 审计必须说明尚未核对历史附加约束，不能宣称已经覆盖整个旧 Bundle。

终态旧 Record 默认保持原格式不写。仍在运行、需要终态更新的旧 Record，可在该 Run 已授权维护中原地升为 schema 2，在正文保留历史 Plan 修订出处；不双写新旧 Record、不修改实际启动事实。`docs check/sync` 本身不迁移源文档。

不新增自动 `docs migrate` 命令。旧读取分支只处理真实持久数据，不继续生成 Plan/Tasks 或恢复旧审批流程。外部安装是否仍需读取旧 Record 是删除这个分支的依据，不能凭框架版本号直接删除支持。

## 6. 安装与升级

沿用现有 CLI，一次安装全部九个保留技能：

```sh
hello-scholar install codex
hello-scholar install claude --mode copy
```

首次安装和后续更新都处理完整的当前技能集合，不增加技能选择参数、安装分组、模型 profile 或多套技能目录。

继续由现有发现器扫描 `skills/*/SKILL.md`，不新增核心技能白名单。仅维护升级需要的退休名称列表；安装测试检查当前九个技能全部可发现并安装，退休名称与当前集合不重叠。

升级先盘点，再改变受管目标：

| 目标 | 自动处理边界 |
| --- | --- |
| 当前源下的受管有效链接 | 更新或保留 |
| 明确指向当前源下退休名称的链接，包括断链 | 仅清除安装链接，保留源及项目数据 |
| 指向别处的链接或来源不明目录 | 保留并报告路径和原因 |
| 有安装基线且内容未修改的受管 copy | 更新；退休技能可清理 |
| 有用户修改、基线缺失或标记不能确认归属的 copy | 保留并报告，不通过 marker 存在就覆盖 |
| AGENTS/CLAUDE 管理块外的文字 | 原样保留 |
| 与当前模板一致的管理块 | 直接重装，无需重复确认 |
| 与当前模板不同的管理块 | 保留；确认替换后更新，模板升级与用户修改均按此处理 |

根据试用反馈，安装器不再读写 `.agents/.hello-scholar-install.json` 或 `.claude/.hello-scholar-install.json`，规则块直接与当前模板比较；卸载只移除与当前模板一致的规则块，旧文件不自动清理。copy 技能目录内原有的 `.hello-scholar-install.json` 仍用于识别技能归属及安装后修改，不记录业务内容。

只要存在必须解决的安装冲突，先输出完整目标列表并结束，写入前不做部分升级；用户决定后执行获准目标。没有冲突的重复安装应可自动完成。安装中途 I/O 失败仍报告实际结果，不宣称成功。

卸载扫描受管目标和退休清单，使用相同的归属检查，不仅遍历当前九个源目录；保留项目文档、运行证据、未知来源或用户修改的副本。升级不能通过简单重新安装 copy 模式抹掉用户定制。

### 本地压缩包交付

实际 npm 包会省略根 CLAUDE 符号链接，原来的按工具选源会导致 Claude 安装 ENOENT。现统一读取 AGENTS 正文，目标规则路径和技能目录不变；缺少唯一来源时在任何安装写入前失败。根通用规则正文不因打包而改变。

`package.json.files` 保留 `bin/`、`src/`、`skills/`、`AGENTS.md`、README、LICENSE，npm 自动纳入 package.json。保留完整技能资源和现有 CLI 所有运行模块，排除历史评测、开发缓存、项目实验和归档；不新增依赖、构建规则正文或生命周期脚本，不改版本及 private。

保留 README 的源码直装与本地总览导航，新增本地 tgz 离线安装方式。link 指向当前 CLI 来源（checkout 或已安装包），该来源必须持续存在；copy 与已写出的规则文本不依赖来源继续存在。

验收使用真实 `npm pack` 产物和离线 npm 安装，删除临时打包源码后核验 Codex/Claude × link/copy 四组合；逐文件比较全部技能资源，验证重装、双工具共存、模式切换和卸载，再移走安装包核验 copy 可读。测试仅复制受控源码输入，并在保留实际 manifest/ignore 的快照中加入排除哨兵，不遍历工作区被忽略的实验、大文件或个人数据。现有归属保护测试继续覆盖用户修改与冲突；测试产物留在临时目录并清理。

这项设计先在真实源码副本保存为 Spec，再由独立会话实施；审查发现的测试复制范围和本地 README 导航问题由主 Agent 修正后才进入当前交付。原始 Spec 与模型过程是验收材料，当前已采用的交付边界由本节维护。

## 7. 初始实施顺序与文件边界

本节保留最初的工程拆分；当前进度和剩余任务以页首总览为准。

每一阶段包含对应检查，不再拆成需要用户逐个批准的微任务。先确立质量基线，再修改技能；文档模型、协作说明和安装升级共同完成后才对外更新，尤其不能让 link 用户先收到删除了技能、但 CLI 尚未支持的新流程。

| 阶段 | 主要修改 | 通过条件 |
| --- | --- | --- |
| 1. 确定质量标准与基线 | 真实案例、可观察结果、无技能与当前技能对照、保留测试集 | 未修改技能前已明确如何判断好坏；基线成功案例也参与对照 |
| 2. 打通文档模型 | document discovery/validation/index、Record 模板及字段参考、相关 JS 测试 | Spec-only 正常；新旧 Record 可读；历史 Tasks 不控制执行；sync 原子性不退化 |
| 3. 替换协作说明 | AGENTS、安装模板、全部九个技能、中英文镜像、删除退休入口 | 一条 Spec 实施请求能到验收；只审计保持只读；没有旧 Skill 调用或镜像前置条件 |
| 4. 完成安装升级 | cli/install/fs-ops/skill-discovery、必要的安装状态、安装测试 | 默认九个；重复安装幂等；退休链接处理正确；用户内容和定制副本得到保留 |
| 5. 更新维护与迁移说明 | README、迁移说明、技能编写参考、有效测试 | 文档只描述最终行为；旧模型和冻结评估不被改写；历史数据迁移边界清晰 |
| 6. 验证用户工作流 | 按质量方案评估各技能及全部安装后的组合 | 每个结论有对应证据；能区分结果改善、回归、等价和证据不足 |

主要现有代码边界是 `src/document-discovery.js`、`src/document-validation.js`、`src/index-generator.js`、`src/cli.js`、`src/install.js`、`src/fs-ops.js`、`src/skill-discovery.js`。复用当前受限 Front Matter 解析器；本方案未引入嵌套 metadata，不需要更换解析库。

确定性验证使用现有 `test/test_document_validation.js`、`test/test_document_discovery.js`、`test/test_index_generator.js`、`test/test_cli_docs.js`、`test/test_cli_install.js` 等。删除只要求旧流程固定措辞的活动测试，将仍有业务意义的断言改为可观察契约；冻结历史 fixtures 和历史模型证据保留原义。旧技能从当前产品覆盖分母移除，不能继续要求它们提供新版本通过结果。

## 8. 验收标准

1. AC-01：只有一个合法 Spec 的项目可执行 docs check/sync，不出现缺少 Plan/Tasks 的诊断；没有任何文档的项目仍成功且不创建空文件。
2. AC-02：收到明确实施请求且 Spec 无关键缺口时，Agent 完成实现与相关验证；不生成 plan.md、tasks.md，不要求阶段审批或完整 tracker 镜像。
3. AC-03：实施途中可对照 Spec 审计，能指出未实现项；仅审计时不写代码、源文档或索引。
4. AC-04：没有平台 tracker 的新会话可从 Spec、代码和证据继续；多个无法区分的目标才需要选择，不按文件时间猜测。
5. AC-05：范围内现有架构文档随实现更新，无需独立 Hash 批准；只有分析请求时不写，无法确认的系统事实不写成已实施。
6. AC-06：Record schema 2 不依赖 Plan；旧 Record 的身份、关联、日志和结论保持可读取；检查与同步不改写源记录。
7. AC-07：默认安装全部九个保留技能；沿用现有安装命令，重复安装不重复插入指令块。
8. AC-08：退休 link、断链、copy、用户修改、其他源链接和管理块冲突分别得到正确处理；无法证明可替换时写入前报告冲突。
9. AC-09：当前任务的显式语言要求覆盖默认语言，中英文入口没有语义相反的授权或停止规则。
10. AC-10：相关确定性回归通过；活动内容无退休技能调用、Tasks 执行门和错误的 system prompt 优先级说明；历史引用作为历史保留。

11. AC-11：九个技能均有明确的结果指标和真实正反案例；发布候选具有独立保留案例的对照证据，报告严重失败、质量变化、触发错误及成本，不由总平均分掩盖单项退化。

模型评估执行 [技能质量评估方案](skill-quality-evaluation.md)，分别判断能否完成任务、相比无技能的额外价值、相比当前版本的变化和九个技能一起安装后的影响。预算和停止条件在运行前固定，付费评估不混入 npm test。实施阶段使用获授权的 `gpt-5.6-sol` 子 Agent 完成了一个 handoff 开发案例的双组、两次重复对照；这不替代 AC-11 所要求的独立保留案例及正式目标模型证据。

## 9. 交付与回退

先在独立开发版本完成质量基线、模型与技能修改、安装升级和维护说明，以临时项目验证新装、升级和旧数据读取，并完成对应质量验收，再向现有 link 用户更新。对需要迁移的用户数据保留原件或可恢复备份；升级技能和 CLI 不自动迁移业务文档。

新旧版本应允许并排保留用于回退。旧 CLI 不能读取 schema 2 Record；切回旧 CLI 时使用升级前的副本或对应安装，不把新 Record 降级覆盖成旧格式。正式切换前在临时项目实际走一遍升级和回退路径。

方案完成的判断是用户可以凭 Spec 连续推进工作，且设计、运行证据和已安装资产都能解释和恢复。本轮方案可直接作为后续实施依据，无需再编写一份强制 Plan 和 Tasks。
