# 技能质量如何判断

日期：2026-09-06。本文定义 hello-scholar 技能改进的质量标准；所有九个保留技能默认安装。安装范围由用户决定，评估结果用于修订技能和说明收益，不自动变更安装范围。

本文维护评价方法，不维护进度；当前执行范围、会话上限和剩余任务统一见 [项目改进总览](spec-driven-skill-design.md)。下文历史验证顺序和命令是方法参考，不构成额外待办或新授权。

## 1. 判断原则

高质量技能应让目标用户在真实任务中得到正确、完整、可以继续使用的结果。对于 Spec 和 Record，保存并复用文档位置、格式、字段含义、修订和证据约定本身就是产品价值：用户安装后描述目标，不必每次重新提供这些要求。技能写得短、被成功调用、遵循全部标题或被模型打了高分，都不能单独证明结果可用。

先判断结果是否合格，再分别回答：用户是否无需重复提供约定；约定已知时，技能的额外指导是否改善结果或稳定性；用户和模型付出的代价是否合理。正确性不能被省 token、速度或表达分数抵消。没有技能也能达到相同结果时如实记录；如果对照输入已经提供了格式契约，打平只说明本案例未观察到额外指导收益，不能用来否定约定复用价值。

## 2. 结果质量先于总分

| 维度 | 要判断的事 | 证据 |
| --- | --- | --- |
| 正确性 | 是否符合实际代码、输入、数据和用户约束 | 可执行检查、事实来源、可复现反例 |
| 完整性 | 关键结果是否交付，是否遗漏会改变决定的边界 | 预先定义的任务验收项，而非 Skill 标题清单 |
| 可用性 | 用户能否只描述目标，下一位执行者能否直接使用结果 | 是否无需补充文档格式，下一步真实任务能否成功、是否需要重要返工 |
| 触发与范围 | 该用时能否使用，不该用时是否干扰正常任务 | 全部技能安装下的调用轨迹和实际副作用 |
| 稳定性 | 换一种说法、输入规模或会话是否仍可靠 | 独立案例、重复运行、保留测试集 |
| 成本 | 用户和模型为结果付出了多少额外工作 | 用户重复提供约定的负担、不必要提问、返工、工具调用、tokens、耗时 |

每个案例先定“不可用、需重要返工、可直接使用”的证据锚点。事实无法核实时标“证据不足”，不把未知记为通过。必要的语义澄清不计为多余提问；正确拒绝或报告真实阻塞可以是合格结果。

用户修改丢失、伪造验证、违反当前任务授权、正式实验关键证据被覆盖属于该候选版本的严重失败，不能被其他案例平均分抵消。评估样本中没发生严重失败，只能说明这批样本没有观察到，不能证明风险为零。

## 3. 九个技能分别证明什么

| Skill | 最重要的结果 | 有意义的验证与反例 |
| --- | --- | --- |
| `manage-specs` | 用户不必重复格式约定，即可保存决定、形成可实施且无关键歧义的 Spec | 自然请求下正确选择归属、路径与修订；独立执行者据此实现；检查遗漏决策、误改约束和重复确认，不奖励七个标题齐全 |
| `record-experiment` | 用户不必重复记录约定，别人仍能定位真实运行、复现输入并正确理解结果 | 自然请求下建立合法 Record；核对实际命令、原始日志、退出码、配置与产物；失败、负结果、同名 Run 冲突、普通 smoke 不应建 Record |
| `converge-to-spec` | 找到真实的重要偏差，控制误报 | 已知缺陷与无缺陷案例，计算有效发现比例及关键缺陷覆盖；未知的新发现独立复核，允许“没有发现问题” |
| `docs-maintenance` | 文档反映当前系统并保留不受影响的事实 | 对比代码与文档事实；check 零写入，sync 幂等，更新不把未来设计写成现实 |
| `handoff` | 新会话能够正确继续工作 | 新执行者只拿项目和 handoff 完成后续任务；测漏掉的约束、重复探索、返工和错误下一步，不按总结长度评分 |
| `grilling` | 解决最有影响的未决选择 | 固定用户决策资料，观察问题是否揭示真实矛盾、是否优先解决高影响选择、何时停止；不奖励问题数量 |
| `crash-audit` | 指出有依据且会改变决定的盲区 | 有已知盲区和无重要盲区两类案例；检查误报、重要遗漏和建议的验证是否可行，不奖励风险数量 |
| `takeoff` | 提出值得考虑且尊重真实约束的目标调整 | 有益重构方向和确有外部契约的反例；比较收益依据、取舍及可证伪性，不奖励更激进或更多删除 |
| `landing` | 给出仍保留目标价值的可行范围 | 用固定资源、时限、数据和兼容条件检验方案；检查主要约束是否满足、验证与停止条件是否可执行，不奖励一味缩小 |

开放式方案没有唯一标准答案。评估者依据事实、约束和后续用途判断是否成立，允许不同但同样可行的设计。用户对方向和价值的偏好应在场景输入中明确，不能由评分者临时猜测。

## 4. 如何得到可信的对照

### 约定复用验收

在实际安装通用规则和全部技能的项目中，给用户自然会提出的目标与业务约束，不另向请求中塞入 schema、路径、必需字段或模板。模型应自行发现适用技能及资源，产出可被项目和下一位执行者使用的文档。现有项目本来就有的格式契约仍保留；不删除真实资料制造困难，也不把测试要求写进实验脚本来提示答案。

用实际读取轨迹、产物、文档 CLI 和下游用途确认：格式与归属正确、业务事实完整、用户没有被要求重复已安装的约定、操作范围符合请求。已验证的同版本自然请求可以复用，不为新报告重复运行。单个成功案例支持该场景的约定复用能力；稳定性需要另有重复或跨项目证据。

这是安装后产品能力的验证，不必要求裸模型猜中它从未获得的私有约定。通用 AGENTS 与技能共同提供的价值按系统能力报告，不仅凭一次成功就归因到某个技能。若要比较用户负担，应保留无技能组实际需要补充的格式说明和澄清，不把用户付出的这些输入当作零成本。

### 额外指导对照

在相同模型、项目快照、用户请求、AGENTS、其他技能、工具和预算下比较：A 不提供目标技能；B 提供当前目标技能；C 提供修改后目标技能。合并技能时 B 使用原有相关组合，明确测量的是组合替换，不能归因到某一句提示。

A 仍获得相同用户请求与独立于技能存在的业务事实，包括项目已有的持久格式契约；不删除任务本来就需要的需求或外部资料来人为削弱基线。为单独观察额外指导的影响，也可以给两组同一份格式契约，但必须声明这一控制已经补上了技能的约定传递功能。技能新增的指导或资源是比较的处理变量，记录实际加载了什么；这种对照不回答用户能否免于反复输入格式。

单独测试技能正文时可显式加载对应版本。测试实际触发时则安装完整目录，给自然语言请求，不强迫模型调用指定技能。两类结果分别报告；只测显式调用不能证明描述写得好或不会误触发。

即使 A 已成功，也继续比较 B/C，记录相同、改善或退步。整套新版 AGENTS、CLI、技能一起替换的结果另列为系统比较，不能将这种多因素变化冒充单技能增益。

### 案例和重复

从真实使用记录中选案例，覆盖常见任务、复杂边界、事实不足、不应触发及正确结果本来就是“无需改动”的情形。把用于改技能的开发案例与最终保留案例分开；看到保留案例后又为它修改技能，该案例就不再是独立验收证据，需要新的保留案例。

初轮对照的每个选定案例每组运行两次用于发现明显问题，不能据此宣称统计稳定。单次产品能力检查则按其实际范围报告。是否追加独立案例或重复，取决于用户要解决的未决问题和授权，不为了让平局变成胜出而继续运行。记录全部运行，不只留下最好的一次。顺序交错或随机化，使用独立临时项目，避免前一组留下的修改、缓存或对话污染后一组。

对于 grilling 等多轮场景，事先固定用户可提供的事实和决策原则，按语义问题提供一致答案，不向某组额外泄露提示。真实用户测试用于验证用户价值，但应记录用户和场景差异，不当作严格控制实验。

### 评价者

可执行检查优先证明确定性结果；下游执行优先证明 Spec 和 Handoff 可用性；开放式判断用匿名成对比较，随机调换左右顺序，允许平局和不确定。评分者能看到任务事实和结果证据，看不到期望哪个版本获胜或技能作者的自评。

模型评分必须逐条给出可核验的理由。作者自评只用于修改建议，不能作为唯一通过依据；关键争议与严重发现需要独立复核。隐藏版本标签可以减少偏见，但文本风格可能暴露来源，因此不能声称完全消除了评判偏差。

## 5. 如何决定是否变好

按本次实际验证的问题汇报：约定复用看自然请求、用户补充负担和产物可用性；额外指导对照看成对胜/平/负/未定、关键遗漏、误报、严重失败、干预与调用开销。单次能力检查不生成虚构的对照结论。每项均标明覆盖范围，不将九个技能的平均分作为某一个技能合格的证据。

检测型技能区分有效发现比例与已知重要问题覆盖率；没有已知问题时，不计算没有意义的覆盖率，改报是否误报。生成型技能优先看是否能直接使用及后续任务结果，不能只比文本的流畅程度。

保留以下结论，不强迫每次优化都获胜：

- 约定复用已验证：用户只描述目标与业务约束，模型通过安装资源生成可用产物，没有索取已提供的格式约定；注明具体场景和次数。
- 额外指导有收益：在同等已知约定下，独立案例出现可重复的质量或稳定性改善，且没有未解决的重要退步。
- 质量相当、成本改善：任务质量与必要证据不下降，额外干预或成本减少；只能宣称效率改善。
- 尚未证明额外指导收益：样本不足、结果接近或仅开发案例改善；不据此否定已有约定复用证据。
- 有退步：出现重要遗漏、错误决策、过度触发或严重失败，修复后重新验证受影响能力。

实际重要的改善幅度在运行前按任务约定，例如减少一个会导致错误实现的关键遗漏。初轮缺少基线数据时属于探索，不事后挑选有利阈值。不存在适用于所有技能的“模型打分 90/100 即可发布”。

本轮默认安装九个技能的决定保持有效。没有具体缺陷时，不因对照打平就改写技能、增加规则或继续找失败基线；只有实际遗漏、冲突、误触发或不必要步骤才支持针对性修订。不自动删除技能或改为单独安装。

## 6. 复用和调整现有评估

现有 `test/skill_eval_contract.py` 可复用证据绑定、输入隔离与历史完整性思想。现有表达质量 rubric 可以辅助评价可读性，但不能替代事实正确性与下游结果。

当前旧协议的 `control-pass must stop before Live Eval` 会阻止基线成功后的比较。新比较协议必须接受基线成功，不要求刻意构造无技能失败；保持旧协议和冻结历史原义，不给历史结果换模型名或重写分数。

新评估结果采用最小的可核对记录，包含场景与版本、实际模型、项目输入、评价标准、各组结果及证据。结构校验只证明记录完整，行为检查与独立复核才证明结果质量；报告必须区分两者。不为新的指标创建重复审批链。

## 7. 本次实施的验证顺序

1. 固定九个技能的结果标准及少量真实案例，先确认评估能识别有意遗漏、错误结论和不必要停顿。
2. 先以 handoff 做完整的小型对照：其价值可以通过下一会话是否正确续做来观察。随后覆盖 Record 与 Spec 对照审计，以及开放式判断技能。
3. 修改技能时运行相关确定性检查；候选稳定后用未用于改写的案例和独立执行者评估。
4. 在九个技能全部安装的环境中检查自然触发、组合请求、小修复与跨会话继续，核对整体结果。

用户已授权使用 `gpt-5.6-sol` 子 Agent，可先用它做有明确边界的实施与行为试验。其结果必须标记为 Sol 的证据，不能据此声称已经验证 GPT-6。正式 GPT-6 评估需实际可用的 GPT-6 运行环境与明确预算；没有这些证据时如实保留结论限制。

## 8. 已落地的验证入口

- 后续开发证据分别见 [Record 迭代](record-quality-iteration.md) 和 [Spec 到实施](spec-quality-iteration.md)。前者明确区分最终文件与执行期写入，后者封存设计后交给独立实施者；失败、未知和修订后的单例复验分别报告，不合并成技能收益结论。
- [开发案例](../../test/quality-cases/scenarios.md)给出九个技能的原始事实、任务与正反条件；它们不是通过记录，也不是独立保留集。
- `test/quality-cases/handoff-continuation/` 提供可复制项目、仅交接作者可见的会话事实，以及只给协调者使用的后续行为检查。
- `python3 -B test/quality_comparison.py <comparison.json>` 检查同模型、同输入的完整成对记录及证据摘要，并报告任务合格数、逐项改善/退步、严重失败、胜平负和未知。两组总体都失败也不会隐藏单项退步。
- `PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest discover -s test -p test_quality_comparison.py` 验证比较器能识别成功基线、退步、未知、不一致输入与被改动或越界的证据；它不能证明技能本身有效。

Handoff 案例按 `prepare → writer-finish → evaluate` 三个阶段执行。协调者先建立独立临时目录，把案例的 `context.md` 作为该目录的 `session-context.md`，再运行：

```sh
python3 -B test/quality-cases/handoff-continuation/evaluate.py prepare <trial-root> --model gpt-5.6-sol --environment '<实际环境与隔离方式>'
```

准备阶段生成四个独立项目、候选技能快照和初始文件摘要。每组各两次；无技能组和候选组的交接作者获得相同项目与会话事实，候选组额外获得冻结技能。每位作者只写本组交接，完成后由协调者在启动独立续做者之前执行对应命令：

```sh
python3 -B test/quality-cases/handoff-continuation/evaluate.py writer-finish <trial-root> baseline 1
python3 -B test/quality-cases/handoff-continuation/evaluate.py writer-finish <trial-root> candidate 1
python3 -B test/quality-cases/handoff-continuation/evaluate.py writer-finish <trial-root> baseline 2
python3 -B test/quality-cases/handoff-continuation/evaluate.py writer-finish <trial-root> candidate 2
```

阶段记录检查原有文件未变且仅新增一个交接文件，并封存其摘要；失败时不能直接进入续做。每位续做者使用新会话，只获得本组项目与交接，不获得原会话事实、其他组结果或后续检查器。全部续做结束、确认不再写入后运行：

```sh
python3 -B test/quality-cases/handoff-continuation/evaluate.py evaluate <trial-root>
python3 -B test/quality_comparison.py <trial-root>/comparison.json
```

评价器核对阶段记录、技能快照与交接摘要，并要求固定的 4 个测试实际完成；退出码 0、零测试或导入时提前退出都不能冒充通过。普通断言失败仍是有效的失败结果，原始 stdout、stderr 和异常保留供复核。`test/test_handoff_quality_harness.py` 的 5 个检查覆盖这些运行边界，与比较器测试一起验证工具是否可靠，不给技能语义质量评分。

续做被暂停、超时或需要协调者介入时，保留该次产物并单独记录原因及介入方式，不通过重跑后替换原结果来隐藏异常。仍可检查已有产物，但产物通过不能记为 Agent 自主正常完成；异常原因无法确认时不归因于技能。

这些阶段记录依赖受信协调者在正确时点采集。它们不独立证明模型实际加载了哪个技能，也不提供操作系统级隔离或 token、成本计量；报告需分别说明输入一致性、阶段写入检查、实际任务结果及这些未覆盖项。

实际试验的原始输出保留在独立临时目录，不进入默认安装或冻结历史评测。实施报告只汇报实际完成的检查，并标明未覆盖的模型、技能、触发和稳定性范围。
