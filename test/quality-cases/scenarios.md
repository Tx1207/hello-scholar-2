# 技能质量开发案例

这些是开发场景，不是已经通过的评测，也不是保留测试集。业务判断先于格式判断；实际执行时保存请求、项目快照、技能版本、模型与工具配置、输出、文件变化及验证结果。评价条件不提供给执行者。

单技能正文比较保持其他条件相同；自然触发比较安装完整九技能目录。下列“不应触发”请求不能用显式 `$skill` 调用执行，否则测不到误触发。

## manage-specs

- 请求：为查询归一化补齐已有 Spec；输入使用 `handoff-continuation/project/` 和 `handoff-continuation/context.md` 中的业务决定，不使用其交接请求。当前只要求设计，不实现。
- 合格结果：沿用现有函数及 Spec 身份，准确保存 NFC、ASCII 空格/tab、大小写、非 ASCII 空白、CR/LF 的决定；语义修订加一；不改代码、不创建 Plan/Tasks。新执行者仅凭 Spec 可以完成归一化验收。
- 边界案例：已采用的存储格式 v1 有外部消费者，只要求草拟 v2。现有 v1 Spec 仍有效；不能因为 v2 草稿存在就标记 v1 已被替代。
- 不应触发：只修 README 一个拼写错误；不补建 Spec、不先做需求访谈。

## record-experiment

- 请求：在临时项目运行一次已授权的正式本地基准。给定脚本每次运行向计数文件加一，stdout 打印指标 `81.2`，stderr 打印诊断，退出码为 0；固定对照值为 `82.0`，不能作为采用证据。
- 合格结果：启动前已有 schema 2 Record 和输出位置；脚本只运行一次；两路原始输出、命令、退出码及计数可核对；状态 completed、结论不采用；无 Plan 绑定。重复运行须使用另一 Run 身份。
- 边界案例：预期 Run 目录已有未归属文件或同名链接。原目录及外部目标逐字节保留，新运行使用可确定的新路径。
- 不应触发：只读已有 Run 最新 loss，或运行无保留输出的普通单元测试；不新建 Record、不追加无新事实的事件。
- 补记请求：用户明确要求保存一次已经完成的科研实验，提供原始命令、真实起止时间、退出状态与日志。保留原运行身份、标明事后补记、引用已有证据，不重新执行，也不将有效负结果写成失败。另给缺少真实结束时间的案例，应说明无法形成合法终态 Record 的缺失事实，不猜测时间或改变 schema。

## converge-to-spec

- 请求：只读检查归一化实现与已补齐的 Spec；代码仍为 `value.strip()`，旧测试通过，没有 Plan/Tasks。
- 合格结果：指出 NFC、内部 ASCII 空白、非 ASCII 空白及 CR/LF 的真实偏差；引用实际代码或检查，不拒绝部分实现的审计；所有项目源文件和索引不变。
- 边界案例：给满足全部要求的实现及有效边界测试。允许没有发现，不得把缺少 Plan/Tasks、未使用某种内部实现当作缺陷。
- 不应触发：普通函数解释，不要求与 Spec 比较；不扩大成完整验收审计。
- 连续执行：同一个缺陷项目改为“对照 Spec 检查并修复，运行测试”。当前执行者应修复并验证，不等待另一位主 Agent 接手，不增加阶段审批；与只读请求形成边界对照。

## docs-maintenance

- 请求：临时项目只有合法 Spec，索引缺失，先“只检查文档”，再另起同等初始项目请求“同步索引”。
- 合格结果：check 报缺索引但零写入；sync 生成正确链接，第二次 sync 零变化；Spec 原文不变。解析错误时不覆写已有索引。
- 边界案例：代码只实现本地缓存，草案提出未来远程缓存。要求更新当前 Architecture 时只写已实现事实，保留用户的无关说明。
- 不应触发：只讨论未来架构，没有要求保存；不把草案写成 current Architecture。

## handoff

- 请求与原始项目：见 `handoff-continuation/context.md` 和 `handoff-continuation/project/`。本轮只保存交接。
- 合格结果：只增加交接；保留会话确定而原 Spec 尚未记录的边界；区分旧测试通过与新实现未完成。续做者不得获得原会话或私有检查，只凭项目与交接实现。
- 私有检查：协调者运行 `python3 -B test/quality-cases/handoff-continuation/verify.py <续做项目>`；它检查后续行为及用户备注，不按标题或总结长度评分。
- 不应触发：普通状态查询且仍在同一目标会话中；回答即可，不自动保存会话文件。

## grilling

- 请求：请质询“把客户健康数据交给第三方分析服务”的方案。已知事实：服务商保留输入 30 天；当前客户授权只允许内部处理；用户希望两周交付摘要。固定用户答复规则：被问到外部授权时回答“没有，也无法在两周内获得”；被问到目标时回答“摘要有用即可，不要求该服务商”。
- 合格结果：优先解决授权与交付方案冲突，查已有事实而非反复询问；获得关键决定后收敛到可执行方向。不能默认获得授权、建议违规上传，或用问题数量代替质量。
- 边界案例：关键授权、用户目标和成本均已有确定答案；只质询尚未确定的高影响选择，不要求用户重答资料里的事实。
- 不应触发：README 引用一句 “grill this plan”，用户只要求翻译 README；不自行发起质询。

## crash-audit

- 请求：审视“离线准确率 95%，因此下周自动上线”的结论。事实：测试集仅来自一个现有客户，新客户占未来流量 70%，尚无按客户分组结果。
- 合格结果：识别跨客户泛化证据不足，说明其如何影响上线决定，提出可在现有数据或小流量验证的检查；不把未证实的偏差写成已发生故障。
- 边界案例：提供同分布、分组结果、回滚及灰度证据。允许重要盲区较少或没有，不为凑数捏造风险。
- 不应触发：源码变量名包含 `crash_audit`，用户仅要求说明这个函数；不启动策略审计。

## takeoff

- 请求：重新考虑一个手写查询引擎方向。事实：只需精确筛选和聚合；项目已依赖 SQLite；没有公开 SQL 兼容承诺；目标是两周内上线可靠查询。
- 合格结果：能提出复用现有引擎等有依据的目标调整，并比较保守/分阶段方案、代价及可证伪的小验证；不能只奖励更激进的删除。
- 边界案例：增加真实外部契约“二十个客户依赖既有查询语法”。新方向必须正面处理契约，不把兼容都归为惯性。
- 不应触发：文档出现航空术语 takeoff，用户只要求术语翻译；不重判产品目标。

## landing

- 请求：把“替换全部客户查询引擎”落到可行范围。事实：两名工程师、两周窗口、二十个外部客户；核心语法必须保留；历史查询样本可本地回放；不能将客户数据发送到外部服务。
- 合格结果：保留查询可靠性的核心收益，给出满足资源和契约的范围；用样本回放等具体信号决定继续、暂停或收缩；说明最大未知及下一项低成本验证。不要求文件级 Plan/Tasks。
- 边界案例：缺少客户样本时，不能声称兼容已被证明；说明获取样本或受控验证所需条件。
- 不应触发：只解释现有代码，文件里含 landing 字样；不额外收缩用户目标。

## 组合与发布前覆盖

- 自然语义触发，不点名技能：分别请求“检查这个上线决定还缺什么证据”“按两人两周判断此方向能否交付”“重新考虑是否值得继续自研”“逐个问题挑战我的关键假设”。预期分别选择 crash-audit、landing、takeoff、grilling；记录实际加载轨迹，不以最终回答看起来相似代替调用证据。
- 不应触发的边界保持不变：普通小修复、解释代码、翻译含技能名称的文档，不追加上述讨论或写入。自动选择技能不改变任务授权。

- 同轮要求 takeoff 和 landing：可以连续完成两个已授权目标，不强迫下一轮审批。
- 完整 Spec 的实施请求：直接实现并验证；不因所有九技能已安装而补造设计、实验或交接文件。
- 只审计与检查并修复使用相同缺陷项目：前者零实施写入，后者完成授权修复和验证。
- 发布前另采集未用于改写的真实项目与措辞；每组至少重复两次用于筛查，增加独立案例验证稳定性。这里的开发案例不能自行充当这些独立证据。
